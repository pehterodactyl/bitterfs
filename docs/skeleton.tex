\emph{A btrfs-flavored filesystem: copy-on-write B-trees, extents, and snapshots,
implemented as a Linux kernel module and developed inside QEMU.}

\emph{Stage 2.5 of \href{../ROADMAP.md}{\texttt{../ROADMAP.md}}. Successor to \texttt{journalext}.}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{the-thesis}{%
\section{The thesis}\label{the-thesis}}

\texttt{journalext} answered ``how do I survive a crash?'' with a \textbf{write-ahead log}: write the
change twice, once to the journal and once in place, and replay the journal on recovery.

bitterfs answers the same question with \textbf{copy-on-write}: never overwrite a live block
at all. A modification allocates a \emph{new} block, and because the block moved, its parent
must be rewritten to point at the new location --- which allocates a new parent, and so on
up to the tree root. A transaction therefore commits by writing a fresh root and
\textbf{atomically flipping a single pointer in the superblock}. There is no log, no replay,
and no checkpoint. Recovery is: read the superblock, use the root it points at.

Everything else in this project is downstream of that one idea.

\hypertarget{architecture-the-freestanding-core}{%
\section{Architecture: the freestanding core}\label{architecture-the-freestanding-core}}

The single most important structural decision in this project.

The B-tree, extent allocator, and transaction machinery are written \textbf{once}, in a
freestanding C library that knows nothing about the kernel. It talks to the outside world
through a narrow environment interface --- read a block, write a block, allocate memory,
checksum a buffer. That interface has two implementations: one backed by the kernel's
buffer cache, one backed by \texttt{pread}/\texttt{pwrite} on a file.

\begin{verbatim}
                    ┌───────────────────────────────┐
                    │   core/  (freestanding C)      │
                    │                                │
                    │   btree.c    — search/insert/  │
                    │                delete/split    │
                    │   cow.c      — CoW + refcounts │
                    │   extent.c   — allocation tree │
                    │   trans.c    — commit protocol │
                    │   inode.c    — item helpers    │
                    └───────────┬───────────────────┘
                                │  bitter_env  (the seam)
                ┌───────────────┴───────────────┐
                │                               │
    ┌───────────▼──────────┐       ┌────────────▼─────────────┐
    │  kernel/             │       │  user/                   │
    │  env: sb_bread,      │       │  env: pread/pwrite,      │
    │       kmalloc        │       │       malloc             │
    │                      │       │                          │
    │  super.c  inode.c    │       │  mkfs.bitterfs           │
    │  dir.c    file.c     │       │  bitter-dump             │
    │  snapshot.c          │       │  bitter-fsck             │
    │  → struct *_operations│       │  unit tests (valgrind)   │
    └──────────────────────┘       └──────────────────────────┘
\end{verbatim}

\textbf{Why this matters:} a B-tree split bug found by a userspace unit test costs you thirty
seconds. The same bug found by \texttt{insmod} costs you a kernel panic, a reboot, and a
scroll through \texttt{dmesg}. Push everything you can across the seam into userspace.

\textbf{The constraint it imposes:} \texttt{core/} may not include a single kernel header or libc
header. No \texttt{printf}, no \texttt{malloc}, no \texttt{assert}, no floating point. Everything it needs
arrives through \texttt{bitter\_env}. This is a real discipline --- enforce it with a compiler flag
(\texttt{-ffreestanding\ -nostdinc}) rather than willpower.

\hypertarget{locking}{%
\subsection{Locking}\label{locking}}

Phases 2 through 4 are single-threaded userspace and need no locking at all. From phase 5
the VFS calls in \emph{concurrently} --- two \texttt{lookup}s on different directories, a
\texttt{write} while \texttt{readdir} walks the same tree, \texttt{sync} during either --- and
every one of those paths touches the same B-trees.

\textbf{The constraint.} \texttt{core/} cannot use kernel locks. \texttt{<linux/mutex.h>} is
no more includable than \texttt{<string.h>}, for the same reason. So locking either becomes
another seam operation, or it lives entirely outside \texttt{core/}.

\textbf{The decision: one big lock.} \texttt{core/} is \emph{lock-free by contract} --- it
assumes its caller has already serialised access --- and the kernel module holds a single
mutex, in the superblock's private data, around every entry point that reaches the trees.
The seam gains no lock operations.

This is deliberately the crude answer. It permits no concurrency whatsoever: a
\texttt{readdir} blocks a \texttt{write} on an unrelated file. In exchange it is obviously
correct, it keeps \texttt{core/} portable, and it can be reasoned about without a lock-order
diagram. Finer granularity is a phase 10 exercise, and one worth doing only once the
filesystem works.

\textbf{A mutex, not a spinlock.} Filesystem operations sleep --- block I/O, memory
allocation with \texttt{GFP\_KERNEL}. Holding a spinlock across either is a bug that
\texttt{CONFIG\_DEBUG\_ATOMIC\_SLEEP} (already enabled in \texttt{qemu/kernel.config}) will
catch loudly, which is the good outcome. The bad outcome is the same bug on a kernel built
without it.

\textbf{What the VFS already holds for you.} You do not start from nothing:
\texttt{i\_rwsem} is held on the parent inode across directory operations,
\texttt{s\_umount} across mount and unmount, and the page cache serialises its own
structures. None of that protects \emph{your} trees, which is why the big lock exists ---
but it does mean you are not responsible for the namespace's own consistency.

\textbf{What btrfs does instead}, for contrast: a read/write lock per tree \emph{block}
(\texttt{btrfs\_tree\_lock}, \texttt{btrfs\_tree\_read\_lock}), acquired as the search
descends and released as the path is popped. That is where
\texttt{btrfs\_search\_slot}'s \texttt{write\_lock\_level} parameter comes from --- a search
that may split must take write locks high enough up the tree to cover the split, before it
knows whether one is needed. Read \texttt{fs/btrfs/locking.c} once for the shape of it, and
do not implement it before phase 10.

\textbf{Consolidation question.} The big lock serialises everything, so why does the commit
protocol of §5 still need ordering guarantees? What is the lock protecting you from, and
what is it \emph{not}?

\hypertarget{structure-map}{%
\section{Structure map}\label{structure-map}}

Every structure in the project, which layer owns it, and how they meet. Twelve of
them, in three groups that never mix: what is written to disk, what
\texttt{core/} holds in memory, and what a tool keeps to itself.

\subsection{On disk --- \texttt{format/bitterfs\_format.h}}

All packed, all little-endian, all with their sizes and field offsets asserted
at compile time.

\begin{center}
\begin{tabular}{llp{7.2cm}}
  \toprule
  Structure & Size & Role \\
  \midrule
  \lstinline|bitter_super|   & 512 B & The one structure at a fixed address, and the only one never copy-on-written. Overwriting it \emph{is} the commit. \\
  \lstinline|bitter_header|  & 96 B  & Starts every tree block, leaf and node alike. Self-identifying: csum, fsid, bytenr, generation, owner. \\
  \lstinline|bitter_key|     & 17 B  & \texttt{(objectid, type, offset)}. The unified keyspace; its sort order is the physical order on disk. \\
  \lstinline|bitter_item|    & 25 B  & A leaf entry: a key plus where in the block its payload lives. \\
  \lstinline|bitter_key_ptr| & 33 B  & A node entry: a key plus the child block's address. \\
  \bottomrule
\end{tabular}
\end{center}

How they nest inside one 4096-byte block:

\begin{lstlisting}[style=shell]
LEAF (level 0)                        NODE (level > 0)
+--------------------+                +--------------------+
| bitter_header  96  |                | bitter_header  96  |
+--------------------+                +--------------------+
| bitter_item[0]     | 25 each        | bitter_key_ptr[0]  | 33 each
| bitter_item[1]     |  -> forward    | bitter_key_ptr[1]  |  -> forward
|      ...           |                |      ...           |
|   free space       |                |   free space       |
|      ...           |                +--------------------+
| payload[1]         |  <- backward
| payload[0]         |                160 items, or 121 children,
+--------------------+                in the 4000-byte data area
\end{lstlisting}

\lstinline|bitter_item| and \lstinline|bitter_key_ptr| each \textbf{embed} a
\lstinline|bitter_key|. \lstinline|bitter_super.root| holds the address of a
block whose first 96 bytes are a \lstinline|bitter_header|. That is the whole
on-disk graph: one fixed pointer into a tree of self-describing blocks.

\subsection{In memory, portable --- \texttt{core/}}

None of these are ever written to disk.

\begin{center}
\begin{tabular}{lp{9cm}}
  \toprule
  Structure & Role \\
  \midrule
  \lstinline|bitter_env|      & The handle \texttt{core/} threads through every call: a vtable and the environment's private state. \\
  \lstinline|bitter_env_ops|  & The vtable --- read, allocate, dirty, release. The entire surface between \texttt{core/} and the world. \\
  \lstinline|bitter_buf|      & One block as \texttt{core/} sees it: \texttt{bytenr}, \texttt{data}, and an opaque handle. Three of \lstinline|struct buffer_head|'s twenty fields. \\
  \lstinline|bitter_key_cpu|  & A key in host order --- what a \emph{search} is given, since a lookup key was never on disk. \\
  \bottomrule
\end{tabular}
\end{center}

\lstinline|bitter_key_cpu| is the only one of these with an on-disk
counterpart. Everything else exists precisely because the on-disk form is
unsuitable in memory.

Keys sort by \texttt{objectid}, then \texttt{type}, then \texttt{offset}. That ordering is not arbitrary ---
it is what makes every important operation a \textbf{contiguous range scan}:

\begin{itemize}
\tightlist
\item
  All items for inode 5 are adjacent → \texttt{stat} and \texttt{unlink} touch one region.
\item
  All \texttt{EXTENT\_DATA} for inode 7, in file-offset order → sequential read is a linear walk.
\item
  All \texttt{DIR\_ITEM} for a directory, in hash order → \texttt{readdir} is one traversal.
\end{itemize}

Getting this ordering right is most of the design.

\hypertarget{node-and-leaf-layout}{%
\subsection{Node and leaf layout}\label{node-and-leaf-layout}}

Every tree block, internal or leaf, starts with the same header:

\begin{Shaded}
\begin{Highlighting}[]
\KeywordTok{struct}\NormalTok{ bitter\_header }\OperatorTok{\{}
\NormalTok{    u8     csum}\OperatorTok{[}\NormalTok{BITTER\_CSUM\_SIZE}\OperatorTok{];}  \CommentTok{/* crc32c over everything after this field */}
\NormalTok{    u8     fsid}\OperatorTok{[}\DecValTok{16}\OperatorTok{];}
\NormalTok{    \_\_le64 bytenr}\OperatorTok{;}        \CommentTok{/* this block\textquotesingle{}s own address — catches misdirected writes */}
\NormalTok{    \_\_le64 generation}\OperatorTok{;}    \CommentTok{/* the transaction that wrote it — the CoW witness */}
\NormalTok{    \_\_le64 owner}\OperatorTok{;}         \CommentTok{/* which tree this block belongs to */}
\NormalTok{    \_\_le32 nritems}\OperatorTok{;}
\NormalTok{    u8     level}\OperatorTok{;}         \CommentTok{/* 0 == leaf */}
\OperatorTok{\}}\NormalTok{ \_\_packed}\OperatorTok{;}
\end{Highlighting}
\end{Shaded}

\texttt{generation} is the field that makes CoW auditable: a block whose generation equals the
current transaction's is already fresh and may be modified in place; anything older must
be copied first. That single comparison is the entire CoW decision.

\textbf{Internal nodes} are a flat array of \texttt{(key,\ block\_pointer,\ generation)}.

\textbf{Leaves} grow from both ends: fixed-size \texttt{bitter\_item} descriptors (key, offset, size)
march forward from the header, while variable-length payloads stack backward from the end
of the block. Free space is the gap in the middle. Sketch this on paper before coding it ---
the arithmetic is where the bugs live.

\begin{verbatim}
┌────────┬──────┬──────┬──────┬─────────────────┬────────┬────────┬────────┐
│ header │ itm0 │ itm1 │ itm2 │  ← free space → │ data2  │ data1  │ data0  │
└────────┴──────┴──────┴──────┴─────────────────┴────────┴────────┴────────┘
\end{verbatim}

\hypertarget{superblock}{%
\subsection{Superblock}\label{superblock}}

Kept at a fixed offset (btrfs uses 64KiB; mirrored copies are optional). It holds the
magic, fsid, block size, total size, and --- the only field that actually commits a
transaction --- the \textbf{root tree address} plus its generation.

Keep the superblock small enough to fit in one sector, so the device's atomic-write
guarantee covers it. If it spans sectors, a torn write can leave you with half of one
transaction and half of another, and pure CoW loses its safety property entirely.

\hypertarget{the-core-algorithms}{%
\section{The core algorithms}\label{the-core-algorithms}}

Each is named with a one-line description. Ask when you want to go deeper on any of them ---
that's what the advisory arrangement is for.

\hypertarget{phase-2-keystones-userspace-testable}{%
\subsection{Phase-2 keystones (userspace, testable)}\label{phase-2-keystones-userspace-testable}}

\textbf{\texttt{btree\_search}} --- walks from the root to the leaf that should contain a key, leaving a
path of held blocks behind it.

Everything else calls this. The return convention matters more than the traversal: callers
need to distinguish ``found exactly'' from ``not found, but here is the insertion point,'' and
they need the whole root-to-leaf path retained, because CoW will have to rewrite every
block on it. Design \texttt{struct\ bitter\_path} first; \texttt{btree\_search} follows from it.

\textbf{\texttt{btree\_insert\_item}} --- makes room in a leaf for a new key and payload, splitting if
needed.

\textbf{\texttt{btree\_split\_leaf}} --- the hard one, because leaves hold variable-sized items and
splitting ``in the middle'' is a size decision, not an index decision.

\textbf{\texttt{btree\_del\_item}} --- removes an item and compacts the leaf's payload region.

Balancing/merging on delete can be deferred. An unbalanced tree is slow; a tree that
loses items is broken. Get correctness first, and be explicit in \texttt{docs/LOG.md} about the
debt.

\hypertarget{phase-3-keystone}{%
\subsection{Phase-3 keystone}\label{phase-3-keystone}}

\textbf{\texttt{btree\_cow\_block}} --- given a block and the current transaction, returns a writable copy
of it at a newly allocated address, and patches the parent to point there.

This is the heart of the filesystem. Three cases it must distinguish:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Block's \texttt{generation} == current transaction → already ours this transaction, write in place.
\item
  Block's refcount \textgreater{} 1 → shared with a snapshot, must copy, must \emph{not} free the original.
\item
  Otherwise → copy, and the original becomes free once this transaction commits.
\end{enumerate}

Note the recursion: patching the parent means CoW'ing the parent, up to the root. And note
where the recursion stops --- at the tree root, whose new address is recorded in a
\texttt{ROOT\_ITEM}, which lives in the root tree, whose new address goes in the superblock.

\hypertarget{phase-4-keystones}{%
\subsection{Phase-4 keystones}\label{phase-4-keystones}}

\textbf{\texttt{extent\_alloc}} --- finds a free range of the requested size and marks it in-use for this
transaction.

There is a circularity trap here worth seeing before you hit it: allocating a block
requires updating the extent tree, and updating the extent tree requires CoW, and CoW
requires allocating a block. Real btrfs escapes with delayed refs. The recommended
simplification: keep an \textbf{in-memory free-space map}, rebuilt by scanning the extent tree
at mount, satisfy all allocations from memory during a transaction, and write the extent
tree updates once at commit time. Document the tradeoff (mount cost scales with
filesystem size) in \texttt{docs/LOG.md}.

\textbf{\texttt{extent\_inc\_ref} / \texttt{extent\_dec\_ref}} --- adjust an extent's reference count; free the
range when it reaches zero.

Refcounting is what makes snapshots work and what makes them safe to delete. This is the
one place where an off-by-one silently corrupts data --- a range freed while still
referenced will be handed out again and overwritten. \texttt{bitter-fsck} exists mostly to catch
this.

\hypertarget{phase-5-keystones}{%
\subsection{Phase-5+ keystones}\label{phase-5-keystones}}

\textbf{\texttt{bitterfs\_iget}} --- fetches an inode by number: allocates the VFS inode, reads the
\texttt{INODE\_ITEM}, and populates both the VFS fields and the private ones.

\textbf{\texttt{bitterfs\_lookup\_extent}} --- maps a file offset to a disk address by finding the
\texttt{EXTENT\_DATA} item covering it. The read path's \texttt{namei}.

\textbf{\texttt{trans\_commit}} --- the ordering protocol of §5, and the only function permitted to write
the superblock.

\textbf{\texttt{snapshot\_create}} --- copies a \texttt{ROOT\_ITEM} under a new subvolume id and increments the
refcount on the shared root node.

Worth appreciating when you get there: this function is about twenty lines. All the work
that makes snapshots correct was already done by \texttt{btree\_cow\_block}'s refcount check.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\hypertarget{the-commit-protocol}{%
\section{The commit protocol}\label{the-commit-protocol}}

The one thing that must be exactly right. Write it down in \texttt{docs/COMMIT.md} and treat it
as a contract.

\begin{verbatim}
1. Write every new/modified data extent to disk.
2. Write every CoW'd tree block to disk (fs trees, then extent tree).
3. FLUSH the device cache.            ← barrier: everything above is now durable
4. Write the new root tree block.
5. FLUSH the device cache.            ← barrier
6. Write the superblock, pointing at the new root tree.  (FUA)
7. FLUSH the device cache.
\end{verbatim}

\textbf{Why every step is there.} Steps 3 and 5 are the whole game. Without them the device is
free to reorder, and a superblock that reaches the platter before the tree it points at
leaves you with a root pointing into garbage --- a filesystem that is \emph{more} broken than one
with no CoW at all. On Linux this means \texttt{blkdev\_issue\_flush()} or a \texttt{REQ\_PREFLUSH\ \textbar{}\ REQ\_FUA} bio, and it is the single easiest thing in this project to forget, because
\textbf{omitting it works perfectly until the moment you actually lose power.}

The invariant, stated once: \emph{at every instant, the on-disk superblock points at a
completely written, internally consistent tree.} A crash at any point above either lands
before step 6 (you get the previous transaction, whole) or after (you get the new one,
whole). There is no third outcome, and that is the entire correctness argument for
this filesystem.

\hypertarget{the-cowpage-cache-collision}{%
\subsection{The CoW/page-cache collision}\label{the-cowpage-cache-collision}}

Expect this and plan for it. The generic page-cache write helpers
(\texttt{block\_write\_begin} and friends) assume a \textbf{stable} block mapping: they ask your
\texttt{get\_block} callback where file offset N lives, and then write there. Under CoW, that
answer changes on every single write. The generic path is structurally incompatible with
the thing you are building --- this is exactly why btrfs carries its own \texttt{writepages} and
delayed-allocation machinery instead of using the generic helpers.

Recommended staging:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Read path first}, using \texttt{read\_folio} with an extent-lookup \texttt{get\_block}. Reads don't
  move blocks, so the generic helpers are safe here.
\item
  \textbf{Write path with immediate allocation}: a custom \texttt{write\_begin} that allocates the new
  extent \emph{up front}, records it, and hands back a page mapped to the new location.
  Simpler than delayed allocation and still genuinely CoW.
\item
  \textbf{Delayed allocation} (allocate at writeback, so sequential writes coalesce into large
  extents) only if you want it later. This is where real filesystems earn their
  performance, and it is a project in itself.
\end{enumerate}

Set \texttt{.bmap\ =\ NULL} and \texttt{.direct\_IO\ =\ NULL}. Both hand out stable block addresses to
external callers, and under CoW there is no such thing.

\hypertarget{version-churn}{%
\subsection{Version churn}\label{version-churn}}

VFS method signatures change between kernel releases --- \texttt{mkdir} alone has changed shape
more than once in recent years. \textbf{Pin one kernel version at the start and stay on it.}
\texttt{Documentation/filesystems/porting.rst} is the changelog for these breakages, and
\texttt{Documentation/filesystems/vfs.rst} is the contract itself. Both live in the kernel tree
you're already building.

\hypertarget{testing}{%
\section{Testing}\label{testing}}

Four tiers. Each one catches a class of bug the others structurally cannot.

\textbf{1. Unit tests on \texttt{core/} (userspace, valgrind).} Insert 10,000 random keys, verify
sorted iteration returns all of them. Delete half, verify the rest survive. Force splits at
every position in a leaf. This tier should be the majority of your test code, because
\texttt{core/} is the majority of your logic.

\textbf{2. Image tests.} \texttt{mkfs} → run a scripted mutation → \texttt{bitter-dump} → diff against a
golden output. These catch on-disk format regressions, which are otherwise invisible until
they're catastrophic.

\textbf{3. \texttt{bitter-fsck} as an assertion, not a repair tool.} Run it after every test. It should
verify: every checksum matches; every block's \texttt{bytenr} matches where it was found; the tree
is sorted and balanced; \textbf{every extent's refcount equals the number of references actually
found by walking every tree}; no allocated range overlaps another. That last pair is
where the genuinely frightening bugs live.

\textbf{4. Crash tests in QEMU.} The reason CoW exists.

\begin{verbatim}
boot VM → mount → start a write workload → SIGKILL qemu mid-transaction
        → reboot → mount → fsck → verify the FS is at transaction N or N+1, never between
\end{verbatim}

Script this and run it in a loop overnight. Then, once it passes, \textbf{deliberately delete
the flush in step 3 of §5 and confirm the test starts failing.} If it doesn't, your crash
test isn't testing anything, and you'd rather learn that now.

\textbf{Later:} \texttt{fsstress} and \texttt{fsx} (from xfstests) for concurrent and pathological
workloads, then the xfstests \texttt{generic/} subset --- the same suite the real filesystems are
held to.

\hypertarget{phases-in-detail}{%
\subsection{Phases in detail}\label{phases-in-detail}}

The table gives the exit criterion. What follows is what each phase actually
costs: which files it creates, which decisions it forces you to make, and what
is hard about it. Phases marked \textbf{done} record what was learned rather
than what was planned.

\subsubsection{Phase 0 --- QEMU dev loop \textnormal{(done)}}

\textbf{Produces} \texttt{qemu/kernel.config}, \texttt{mkinitramfs.sh},
\texttt{init}, \texttt{run.sh}, \texttt{guest.sh}, and \texttt{kernel/}'s
\texttt{Kbuild} plus wrapper Makefile and a hello-world module.

Almost none of the work is filesystem work, which is the point: when phase 5
goes wrong you want to already know the loop is sound, so the search space is
your code and not the plumbing.

\textbf{Three things this phase teaches the hard way.} The guest kernel must be
built with \texttt{modules} and not only \texttt{bzImage} --- the former is what
generates \texttt{Module.symvers}, without which modpost fails on undefined
symbols that have nothing to do with your module. Kbuild reads a file named
\texttt{Kbuild} in preference to \texttt{Makefile}, and with neither providing
\texttt{obj-m} it builds nothing and exits zero, which looks exactly like
success. And an out-of-tree module always sets \texttt{TAINT\_OOT\_MODULE}, so
a smoke test asserting an untainted kernel fails forever.

\subsubsection{Phase 1 --- Format and tools \textnormal{(done)}}

\textbf{Produces} \texttt{format/bitterfs\_format.h},
\texttt{core/bitter\_endian.h}, \texttt{core/bitter\_crc32c.\{c,h\}} with its
generated table, and the two tools with their shared \texttt{util}/\texttt{print}
support.

\textbf{Decisions this phase forces, all permanent.} Which checksum, and over
which byte range --- and the answer differs between the superblock (32..512,
because that is the sector the drive writes atomically) and a tree block
(32..4096, because a leaf's items fill it). What \texttt{generation} starts at:
1, not 0, so that 0 can keep meaning "no transaction ever wrote this". Whether
the crc32c table is a literal, computed at init, or generated at build time.
And the numeric values of every item type and reserved objectid, which cannot
change afterwards without invalidating every image ever made.

Write the on-disk documentation \emph{before} the code. A format you cannot
describe in prose you cannot debug at 2am.

\subsubsection{Phase 2 --- B-tree in userspace}

\textbf{Produces} \texttt{core/items.\{c,h\}}, \texttt{core/btree.\{c,h\}},
\texttt{user/env\_user.\{c,h\}}, and the first entries in \texttt{tests/unit/}.

\textbf{The seam stops being optional here.} Phases 0 and 1 got away with
direct \texttt{pread} and \texttt{pwrite} because \texttt{mkfs} and
\texttt{bitter-dump} are ordinary programs. The moment tree code lives in
\texttt{core/}, it needs blocks and cannot call libc for them.

\textbf{What is hard} is not the B-tree --- it is the two-ended leaf. Item
descriptors grow forward while payloads stack backward, so an insert in the
middle has to move both regions and rewrite every following descriptor's
offset. Off-by-one there produces a leaf that reads as plausible garbage rather
than failing, which is why the randomized tests matter more than the code does.
Splitting is the second hard part, and it is where a search that must split
discovers it needed to hold a write lock further up --- an ordering problem
that only exists once phase 5 adds concurrency, but whose shape is set here.

\textbf{No copy-on-write yet.} Modify in place. Adding CoW to a B-tree that
already works is a contained change; debugging both at once is not.

\subsubsection{Phase 3 --- CoW and transactions}

\textbf{Produces} \texttt{core/cow.\{c,h\}} and \texttt{core/trans.\{c,h\}}, and
adds \texttt{writeback\_all} and \texttt{flush\_device} to the seam.

The whole phase turns on one comparison: a block whose \texttt{generation}
equals the current transaction is already ours and may be modified in place,
while an older one must be copied first. That single test is the copy-on-write
decision, and every subtlety in this phase is a consequence of it.

\textbf{What is hard} is ordering. Everything the new tree points at must be
durable before the superblock that points at the new tree, and "durable" means
a device flush and not merely a completed write. Get it wrong and the
filesystem works perfectly until the first power cut. The crash test is
therefore not optional --- it is the only thing that distinguishes a correct
commit protocol from a plausible one.

\subsubsection{Phase 4 --- Extent tree}

\textbf{Produces} \texttt{core/extent.\{c,h\}} and \texttt{user/fsck.c}.

Allocation and reference counting. Until now blocks have come from hardcoded
addresses; from here an allocator hands them out and a refcount decides when
one is free again.

\textbf{What is hard} is the recursion: allocating a block requires modifying
the extent tree, which requires copy-on-writing its blocks, which requires
allocating blocks. btrfs breaks the cycle with delayed refs --- accumulating
reference changes in memory and applying them at commit. Expect to discover
this problem before you find that name for it.

\texttt{bitter-fsck} earns its place here, because a refcount that drifts is
invisible until a block is freed while still referenced, and by then the
evidence is gone.

\subsubsection{Phase 5 --- Mount, read-only}

\textbf{Produces} \texttt{kernel/super.c}, \texttt{inode.c}, \texttt{dir.c}, and
\texttt{kernel/env\_kernel.c}.

The first time \texttt{core/} runs inside the kernel. If the seam was honest,
this phase adds a second environment implementation and changes nothing above
it.

\textbf{What is hard} is that the feedback loop collapses. Everything
\texttt{core/} got wrong that userspace tolerated --- a leaked buffer, a
sleeping allocation under a lock, a stack array that was fine at 8 KB of
userspace stack and is not at 8 KB of kernel stack --- now presents as a panic
and a reboot. The VFS surface itself is mostly boilerplate; the difficulty is
everything upstream arriving at once.

This is also where the single mutex of §1.3 appears, and where lockdep starts
having opinions.

\subsubsection{Phase 6 --- File reads}

\textbf{Produces} \texttt{kernel/file.c} and the
\texttt{address\_space\_operations}.

Extent lookup and \texttt{read\_folio}. The interesting case is the hole: a
sparse file has ranges with no \texttt{EXTENT\_DATA} item at all, and the
correct answer for those is zeroes rather than an error.

\subsubsection{Phase 7 --- File writes}

\textbf{Produces} the rest of \texttt{inode.c} and \texttt{file.c}:
\texttt{create}, \texttt{write}, \texttt{unlink}, \texttt{mkdir},
\texttt{truncate}, \texttt{fsync}.

\textbf{The largest phase} --- expect it to exceed 5 and 6 combined. It is
where the page cache and copy-on-write collide, because the page cache is built
around a page having one stable disk address and CoW moves it on every write.

\subsubsection{Phase 8 --- Snapshots}

\textbf{Produces} \texttt{kernel/snapshot.c} and one ioctl.

\textbf{The payoff, and the audit.} A snapshot is a second root item pointing at
the same tree, with the root block's refcount incremented. If that turns out to
be nearly trivial, phases 3 and 4 were done correctly. If it is hard, something
upstream is wrong --- trust that signal rather than working around it.

\subsubsection{Phase 9 --- Crash consistency in the VM}

No new files. The phase 8 crash loop, run against a real virtio device for
hundreds of iterations.

\texttt{dm-log-writes} is the rigorous tool: it records every write and flush
in order, so you can replay the device to any point and check that what you
find is a filesystem that mounts. That is a stronger claim than "it survived
the power cuts I happened to test".

\subsubsection{Phase 10 --- Extras}

Reflink (\texttt{FICLONERANGE}), snapshot \emph{deletion} (much harder than
creation --- a recursive reference drop), checksum verification on read,
compression, \texttt{xfstests}, defragmentation, and finer-grained locking than
the single mutex.

Pick by what you want to learn. Nothing here is load-bearing for the rest.

\hypertarget{known-hard-spots}{%
\section{Known hard spots}\label{known-hard-spots}}

Flagged in advance so you recognize them rather than discover them.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Allocator recursion} (§4). Allocating requires updating the extent tree requires
  allocating. The in-memory free-space map is the escape hatch.
\item
  \textbf{Leaf splitting with variable-sized items.} Not a midpoint index --- a size-based
  decision, with the possibility that a single item is too large to fit anywhere.
\item
  \textbf{The flush barriers} (§5). Invisible until power loss. Test for their absence.
\item
  \textbf{CoW vs.~the generic page-cache helpers} (§6). Structural, not a bug. Plan the write
  path around it.
\item
  \textbf{Refcount off-by-one.} Silent, delayed, catastrophic. \texttt{bitter-fsck} is the defense.
\item
  \textbf{Locking.} Deferred through phase 7, then unavoidable. Real btrfs uses per-block
  read/write locks with careful path-acquisition ordering. Start with one filesystem-wide
  mutex, get it correct, and let lockdep guide the refinement. A single big lock that
  works beats fine-grained locking that deadlocks.
\item
  \textbf{Snapshot deletion.} Creation is twenty lines; deletion is a recursive walk dropping
  a reference on every block, freeing only those that reach zero, and it must be
  restartable across a crash. Treat it as its own phase.
\item
  \textbf{Kernel API churn} (§6). Pin a version.
\end{enumerate}

\hypertarget{reading-list}{%
\section{Reading list}\label{reading-list}}

\textbf{Primary sources.} Ohad Rodeh, \emph{``B-trees, Shadowing, and Clones''}~\cite{Rodeh_2008}
--- the paper btrfs's design comes from, and the source of the refcounting scheme in §4. Read it
before phase 3. The later btrfs paper~\cite{Rodeh_2013} is the same ideas as shipped, and is the
shorter read. Chris Mason's original btrfs design notes. The btrfs on-disk format
documentation~\cite{btrfs_docs}.

\textbf{Code.} \texttt{fs/btrfs/ctree.c} in the kernel tree --- \texttt{btrfs\_search\_slot} and
\texttt{btrfs\_cow\_block} are the functions you are reimplementing; read them once early and again
after your own version works. \texttt{btrfs-progs} for the userspace/kernel code-sharing pattern
of §1. \texttt{sysprog21/simplefs} for a minimal disk-backed kernel module, which is the clearest
model for phase 5.

\textbf{Checksums (phase 1).} Ross Williams, \emph{``A Painless Guide to CRC Error Detection
Algorithms''}~\cite{Williams_1993} --- an hour of plain text, and the only CRC tutorial worth
reading. It derives the algorithm from polynomial division rather than asserting it, and it is the
place to understand \emph{reflection}: why the constant you type is \texttt{0x82F63B78} rather than
the \texttt{0x1EDC6F41} everyone quotes, and why the shift goes right. Those two choices are
invisible in finished code, so without this the implementation is a magic number and a coin flip.
Williams also introduces the Rocksoft parameter model that pins a CRC exactly, which is what Greg
Cook's catalogue~\cite{crc_catalogue} then tabulates --- look up \textbf{CRC-32/ISCSI}, since
``CRC-32'' alone names about twenty different algorithms and that ambiguity is why a correct
crc32c disagrees with \texttt{cksum}, \texttt{zlib} and \texttt{gzip}. For implementation
strategies once the theory is in place, Stephan Brumme compares bitwise, table-driven and
slicing-by-8 side by side~\cite{brumme_crc32}, and the kernel's own
\texttt{lib/gen\_crc32table.c} shows a third option: generating the table at build time rather
than at init. Optional background: Castagnoli's paper~\cite{Castagnoli_1993} on why this
polynomial was chosen, and RFC 3720~\cite{rfc3720}, which standardised it for iSCSI and gave it
the catalogue name.

\textbf{Kernel.} \texttt{Documentation/filesystems/vfs.rst} (the contract),
\texttt{Documentation/filesystems/porting.rst} (the churn), and --- since you've already read xv6's
\texttt{namex} and \texttt{bmap} --- note that \texttt{bitterfs\_lookup\_extent} is what \texttt{bmap} becomes when block
pointers give way to extents.

\hypertarget{consolidation-questions}{%
\section{Consolidation questions}\label{consolidation-questions}}

In the style of the roadmap. Revisit at each phase.

\begin{itemize}
\tightlist
\item
  Where did the answer to ``\emph{what happens if the machine crashes between the journal commit
  and the checkpoint?}'' go? Why does the question stop making sense here?
\item
  CoW never overwrites live data, so why does bitterfs still need a device flush?
\item
  What does CoW cost that journaling doesn't? (Consider: a one-byte write to a file inside
  a deep directory tree. How many blocks are written?)
\item
  Why is a snapshot O(1) to create but not O(1) to delete?
\item
  If an extent is shared by two snapshots and one of them overwrites the middle 4KiB of it,
  what happens to the other 99\% of the extent? Which \texttt{EXTENT\_DATA} field makes the answer
  efficient rather than ``copy the whole thing''?
\item
  Why does fragmentation hurt CoW filesystems more than in-place ones? What is \texttt{balance}
  actually for?
\item
  Your \texttt{bitter\_env} seam exists to keep \texttt{core/} out of the kernel. What did that cost you
  in the kernel implementation?
\end{itemize}
